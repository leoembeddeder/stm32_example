stm32_uds_iso_tp: Detailed Improvement Plan

Based on a fresh build of main (commit 34ab85b, 107 commits), a strict-warning compile of every source file, GCC -fanalyzer, and cyclomatic-complexity measurement with lizard. Everything below is tied to something I measured or read in the code. Items are ordered by payoff.

Measured baseline

  • 23/23 host tests pass.
  • Library sources compile with only 1 warning under -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion -Wshadow -Wcast-qual and friends. The analyzer reports nothing. This is a clean base to build on.
  • 310 functions, average complexity 6.1, but 28 functions exceed complexity 15 or length 80. A handful are extreme (see P0-1).
  • No fuzzing, no MISRA check, no coverage threshold, VERSION file not wired into the build.

Correction: an earlier version of my roadmap said the AES-CMAC code had no known-answer tests. That was wrong. tests/crypto/test_aes_cmac.c contains all four RFC 4493 vectors, and a constant-time comparison exists. I have fixed that page.

P0: Fix the structural cause of the bugs

P0-1. Break up uds_dtc_app_report (480 lines, complexity 201)

Evidence: App/Src/uds_dtc_app.c:305 is one function with a switch over every 0x19 sub-function. Complexity 201 is roughly 10x the usual "must refactor" limit. The open and recently closed bugs cluster in this file: #55, #56, #58, #64, #65, #72. That is not a coincidence. A function this large cannot be reasoned about or fully tested.

Fix: make the sub-functions table-driven, and let each handler do one thing.

typedef struct {
    uint8_t  subfunction;
    uint8_t  min_len;            /* request length check lives in data */
    uint8_t  max_len;
    UdsCallbackResult (*handler)(const DtcReq *req, DtcResp *resp);
} DtcSubfnEntry;

static const DtcSubfnEntry k_dtc_subfns[] = {
    {0x01, 3, 3, dtc_report_count_by_mask},
    {0x02, 3, 3, dtc_report_list_by_mask},
    {0x04, 6, 6, dtc_report_snapshot_by_dtc},
    {0x06, 6, 6, dtc_report_extended_by_dtc},
    {0x0A, 2, 2, dtc_report_supported},
    /* ... */
};

Then uds_dtc_app_report is about 20 lines: validate, look up, dispatch. Note that library/src/uds_dtc.c already has three functions (uds_dtc_subfunction_supported, ..._request_length_valid, ..._capability_for_subfunction) with complexity 28 to 33 that are themselves hand-written tables. Merge them into the same table so supported-ness, length rules and capability come from one row.

Also: move the DTC logic out of App/ into library/ (see P1-1). App/ should only hold board glue.

Acceptance: no function above complexity 15. One unit test per sub-function, including "after 0x14 clear, every list sub-function returns an empty list" (the exact regression from #65).

P0-2. Single source of truth for DTC state

Evidence: #65 was "clear and read are not linked". #72 was "DTC codes wrong again after update". The library has both a seeded ROM table (s_rom_dtc_defs), file-scope storage (s_dtc_storage), and NVM persistence, read through get_dtc_record().

Fix:

  1. One DtcStore struct owns records. Every path (report, clear, event report, NVM load, ROE) goes through four functions: dtc_store_get, dtc_store_set_status, dtc_store_clear, dtc_store_iterate.
  2. Add a property test: run a random sequence of report/clear/event operations and check that 0x19 0x01 count always equals the number of items 0x19 0x0A returns.
  3. Version the NVM record format (magic + version + CRC). When a firmware update changes the layout, migrate or reject cleanly instead of showing garbage. #72 looks like exactly this failure mode, which is worth confirming.

P0-3. Make flash programming granularity a port property (#91)

Evidence: UdsFlashPort has erase/read/write/sector_size only. UdsParamSlotHeader is a fixed 16-byte struct. STM32F1 programs 2 bytes, F4/F7 up to 4 bytes with parallelism, L4/G4 8 bytes, H7 32 bytes. The reporter's question in #91 is legitimate.

Fix: add granularity to the port and compute slot layout at init.

typedef struct {
    int      (*erase)(uint32_t addr);
    int      (*read)(uint32_t addr, void *buf, size_t len);
    int      (*write)(uint32_t addr, const void *buf, size_t len);
    uint32_t (*sector_size)(uint32_t addr);
    uint8_t  program_granule;   /* 2, 4, 8, 16, 32... must be power of two */
    uint8_t  erased_byte;       /* usually 0xFF */
} UdsFlashPort;
  • Round slot_size up to a multiple of program_granule, and pad the header with erased_byte.
  • Make the header two-phase: write the payload first, then commit with a separate header-commit granule, so a power cut between the two leaves an invalid (ignorable) slot.
  • Add host tests with a fake flash that enforces the granule (rejects misaligned or partial writes and forbids rewriting non-erased bytes). Run the whole test suite for granules 2, 4, 8, 16 and 32. This proves portability instead of claiming it.
  • Also test power loss: inject a failure after every single write call and check the store always recovers to the last committed value.

P0-4. Formalise the "closed but not verified" gap

Evidence: #62 and #68 are still open although a commit says "resolves" them; #56 and #58 the same. #76 is closed but its commit was reverted.

Fix: adopt "closed means verified". Use Fixes #N only in the merge commit that actually lands, close only after the reporter confirms on hardware or a regression test references the issue number, and add a needs-hw-confirmation label as the waiting state. For every fixed bug, add a test named after the issue (test_issue_65_clear_then_read_is_empty).

P1: Architecture

P1-1. Move protocol logic out of App/ into library/

Evidence: App/Src/uds_dtc_app.c (1302 lines) and uds_bootloader.c (1100 lines) hold real logic, but only library/ is HAL-free and host-tested. App/ includes STM32 headers, so it cannot be fully tested on a PC. The collaborator's repeated "port this to my stm32f103" requests are the cost of this layout.

Target layout

library/   HAL-free, host-tested: isotp, uds core, dtc, did, security,
           bootloader state machine, flash fsm, wear leveling, crypto
ports/     one folder per MCU family: f1, f4, f7, c0, g4
           each implements: can_port.h, flash_port.h, clock_port.h, reset_port.h
examples/  thin main() + board config only

A new MCU then means one ports/<family>/ folder implementing four small interfaces. The F103 requests (#71 to #89) would become "ship a ports/stm32f1" once, instead of hand-porting each service into someone's private repo.

P1-2. Split uds_bootloader.c

Evidence: it bundles a hand-written SHA-256, flash programming, slot management, anti-rollback, routine control (complexity 39), and the jump to the application (with __disable_irq).

Fix: split into sha256.c (or a hardware/vetted implementation), boot_slots.c (A/B metadata), boot_verify.c (integrity policy), boot_routines.c (UDS 0x31 glue) and boot_jump.c (the only file with inline asm). Test SHA-256 against the NIST vectors, as CMAC already is.

P1-3. Make the integrity policy pluggable (answers #68)

Instead of maintaining two bootloaders, define one interface:

typedef struct {
    bool (*verify)(const BootImageHeader *hdr, const uint8_t *image, size_t len);
} BootIntegrityPolicy;

Ship policy_crc32 (fast, detects corruption, no security), policy_sha256 (integrity), and policy_signature (ECDSA or Ed25519 for authenticity). Say clearly in the docs that CRC protects against accidents, not attackers. That answers the collaborator's request without duplicating the bootloader and keeps the secure path.

P1-4. Move the flash FSM under the bootloader and DTC NVM

uds_flash_fsm.c (118 lines) is a good start for #69. Use it for every erase/program path (download, wear-leveling commits, bootloader), driven from the main loop with a bounded time slice per tick. Add tests that prove uds_server_process() keeps servicing ISO-TP flow control while a 128 KiB erase is in flight (STmin and P2*/0x78 keep-alives must not starve).

P1-5. Reduce the three biggest core functions

Function Complexity Action
uds_server_handle_addressed (uds.c:1180) 44 table-driven service dispatch with per-service session/security/addressing flags (this also delivers #67 and #73 cleanly)
isotp_rx_feed (isotp.c:203) 32 split into rx_single, rx_first, rx_consecutive, rx_flow handlers
uds_bootloader_routine_control 39 one function per routine ID behind a table

P2: Quality and verification

P2-1. Turn CI signals into gates

  • Coverage runs but only prints. Add --fail-under-line 90 --fail-under-branch 80 for library/.
  • Add -Werror with the strict flag set I used above (only one warning to fix: uds_did.c:40, see P2-4).
  • Add a lizard -C 15 check for library/ (start at 25 for existing code, ratchet down).
  • Add a check that VERSION, the latest tag and CHANGELOG agree.

P2-2. Fuzz the two parsers

Add libFuzzer targets: fuzz_isotp_rx (arbitrary CAN frames into the receive state machine, including malformed PCI bytes and lengths) and fuzz_uds_request (arbitrary bytes into the server across every session/security state). Run 60 seconds per PR and a longer job nightly. Both run under ASan/UBSan, which CI already has. Keep a corpus folder.

P2-3. MISRA C:2012 subset

Add cppcheck's MISRA addon or a commercial checker to the CI, with a written deviation list. The code already uses fixed-width types, U suffixes and no heap, so most rules should pass.

P2-4. Small code fixes found in the scan

  • library/src/uds_did.c:40: entry->context = (void *)value; discards const. A DID registered as read-only can be written through context if a handler misuses it. Store const void * in a read-only entry type, or add a separate context_ro field.
  • Where uds_did.c sets entry->write = NULL for read-only DIDs, add a test that a 0x2E write to it returns NRC 0x31 or 0x33 as appropriate.
  • uds.c:769 service_security_access is 114 lines (complexity 24): extract attempt counter and delay-timer logic into a small SecurityGate struct with its own tests (lockout after N failed keys, delay after power-on, seed reuse).
  • Add negative tests for every multi-byte length field (off-by-one at capacity).

P2-5. Timing validation on real hardware

Host tests inject a clock, so they cannot prove STmin, P2 and P2* on silicon. Measure with a logic analyzer or a CAN analyzer and record the results (see P3-1). At minimum: STmin 0 to 127 ms and the 0xF1 to 0xF9 microsecond range, N_Bs/N_Cr timeouts, and response time under a 90% bus load.

P2-6. Concurrency review

uds_app.c shares an RX ring between ISR and main with volatile head/tail and __disable_irq() in the consumer. That is a workable single-producer, single-consumer design, but volatile alone gives no memory barrier on Cortex-M7 with caches or on multi-core parts. Add __DMB() around head/tail publication on those targets, document the ISR/main ownership rules in one place, and add an overflow-counter test.

P3: Process and evidence

P3-1. Fill in the physical-validation record

27 fields in docs/physical_validation/board_profile.yaml are still TBD and the README still says the campaign is not run, although bench testing is happening in the issue tracker. Use the bench results you already have: for each test ID, record board, firmware hash, tester tool, raw trace, verdict. Even partial, honest evidence lifts this dimension a lot.

P3-2. Release discipline

  • Tag v1.6.0 (11 commits are unreleased on top of v1.5.0).
  • Make VERSION the source of truth: read it in CMake (file(READ ...)), generate uds_version.h, and expose uds_iso_tp_version(). Right now VERSION says 0.1.0 and nothing consumes it.
  • Batch fixes into scheduled releases; put breaking/feature/fix sections in the changelog.

P3-3. Requirements traceability

One CSV/markdown table: requirement (ISO 14229-1 or 15765-2 clause) → source function → test → hardware evidence. Start with the services the tester exercises (0x10, 0x11, 0x14, 0x19, 0x22, 0x27, 0x2E, 0x31, 0x34 to 0x37).

P3-4. Protect maintainer time

  • Add an issue template with "library bug", "feature", "help with my own project".
  • Label porting requests support and answer them with a link to the port guide instead of writing code into private forks.
  • Add a second reviewer and enable required PR review on main. Ask the collaborator to send fixes as PRs.

P3-5. Security follow-ups

  • Independent review of aes.c (table S-box lookups are not cache-timing safe; use the STM32 hardware AES peripheral where present).
  • Signed images plus anti-rollback counters stored in a tamper-resistant location (option bytes/OTP), not plain flash.
  • Rate-limit 0x27 attempts across resets (persist the counter).
