stm32_uds_iso_tp: Deep Review, Prioritized Fix List (P0 to P6)

Scope: repo at v1.6.1 (8d197bc). Issue tracker deliberately ignored, as requested. Method: I built and ran everything (30/30 tests, ASan/UBSan, coverage, 2 x 30 s libFuzzer runs, cppcheck, lizard, strict warnings), then read the security, ISO-TP, bootloader, download and app-glue code line by line. Limits: everything below comes from reading code and running host tools. I did not run any of it on hardware and did not write exploits. Where a claim depends on something I could not see, I say so.

Reading guide

  • P0: security controls that do not protect anything as shipped. Fix before any use outside a lab.
  • P1: standards-conformance and correctness defects, plus dead or duplicated logic.
  • P2: architecture that keeps quality from improving.
  • P3: verification depth.
  • P4: hardware evidence.
  • P5: process and project health.
  • P6: polish and nice-to-haves.

What is already good (so you don't touch it)

  • 0 strict-warning findings in library/ and crypto code; no function above complexity 15 (489 functions, average 4.2).
  • ISO-TP receive path is safe against length underflow: FF/SF header lengths are checked against DLC before any copy (I traced decode_sf, decode_ff, rx_first, rx_consecutive). No out-of-bounds read found.
  • Download range check handles address + length overflow (range_inside, validate_download_region).
  • Wrap-safe timer comparisons ((int32_t)(now - deadline) >= 0) are used consistently.
  • Message-authentication-related test vectors exist for AES-CMAC (RFC 4493).
  • The ISR/main RX queue is documented, uses single-producer/single-consumer ownership and __DMB().
  • docs/standalone/release_audit.md honestly lists secure boot, authenticated images, rollback and anti-rollback as product-owned work.

P0: Security controls that are ineffective as shipped

P0-1. The default "signature" boot policy can be forged by anyone

Evidence: library/src/boot_verify.c, verify_signature_impl. When no verifier is registered (s_sig_verifier == NULL, the default), it computes HMAC-SHA256(mock_key, hdr->sha256) with a hard-coded 16-byte key ("SECURE_BOOT_KEY1", visible in the source) and compares it with the header's signature field. Anyone can compute that value for any image. The policy is labelled "Cryptographic Signature (Authenticity and integrity)".

Impact: a bootloader configured with the "signature" policy and no verifier accepts attacker-built firmware. The label makes integrators believe they are protected.

Fix

  1. Fail closed: if no verifier is registered, verify_signature_impl returns false.
  2. Delete the mock key from production builds; keep it only in the test target behind #ifdef UDS_ISO_TP_TESTING.
  3. Replace "HMAC with a shared key" with a real asymmetric verifier callback (Ed25519 or ECDSA-P256, public key in read-only memory or option bytes). Rename the policy honestly if a symmetric MAC is ever offered (policy_mac).
  4. Compare MACs with a constant-time function, not memcmp (boot_verify.c:57).

Acceptance: test that the signature policy rejects every image when no verifier is set; test that a forged header computed with the old mock key is rejected.

P0-2. SecurityAccess keys are public or trivially derivable

Evidence: App/Src/uds_security_app.c, App/Inc/uds_security_app.h.

  • Level 1: key = seed XOR constant, with the four constants (A5 5A C3 3C) in the public header, 4-byte seed. One captured seed/key pair, or the source, reveals it.
  • Level 2: when no key is provisioned and no custom provider is set, it uses s_default_reference_key, the published NIST AES test key 2B7E1516 28AED2A6 ABF71588 09CF4F3C. The device unlocks for anyone who knows that key, silently.

Impact: security access provides no protection on a default build, and nothing warns integrators.

Fix

  1. Remove the default key from non-test builds. With no provisioned key and no provider, level 2 must refuse seed requests (NRC 0x22 or 0x12) and report "not provisioned" through a diagnostic status.
  2. Delete level-1 XOR from production builds, or mark it DEMO_ONLY and compile it only with an explicit flag.
  3. Provisioning: keys come from protected storage (option bytes, OTP, or a secure element), never from source. Add uds_security_app_is_provisioned().
  4. Per-device keys: derive K_dev = CMAC(K_master, UID) so a leaked device does not expose the fleet.

Acceptance: test that an unprovisioned build cannot be unlocked; a key derived from the NIST key does not unlock a provisioned build.

P0-3. Lockout can be bypassed with an ECU reset or power cycle

Evidence: library/src/uds.c, security_reset_for_ecu_reset sets security_failed_attempts = 0 and security_lockout_active = false. There is no persistence of the attempt counter anywhere (I grepped App/). Separately, uds_security_gate_set_timing / the server accept lockout_ms == 0, which leaves no lockout at all.

Impact: an attacker who can send 0x11 (usually allowed without unlock) or cut power gets unlimited guesses. Combined with P0-2 and P0-5, seeds and keys are guessable at CAN speed.

Fix

  1. Persist failed_attempts (and a lockout-remaining timer) in NVM (wear-leveled store already exists); restore it at boot; write it before answering a wrong key.
  2. Do not clear the counter on 0x11. Clear only after a valid key or after the lockout timer expires.
  3. Enforce a non-zero minimum delay (for example 10 s after 3 failures, exponential afterwards). Reject lockout_ms == 0 in configuration.
  4. Add a power-on delay (ISO 14229 0x37 behaviour) that survives reset.

Acceptance: tests: three wrong keys, then 0x11 01, then a new key attempt → still locked. Power-cycle simulation → still locked.

P0-4. The anti-rollback floor is not restored after reset

Evidence: App/Src/uds_bootloader.c. s_bl_ctx.active_version is assigned in only three places: line 169 and 479 (set to the constant 1) and line 467 (on activation). uds_bootloader_init() loads metadata from NVM (loaded_meta) but never copies loaded_meta.version into active_version. The version check at line 783 (meta->version < active_version) therefore compares against a RAM value that resets on every boot. uds_bootloader_rollback_candidate() also forces it to 1.

Impact: after any reset the check accepts older, possibly vulnerable images. That is not anti-rollback.

Fix

  1. Store a monotonic security version in tamper-resistant storage (option bytes, OTP, or a write-once flash counter), separate from the slot metadata.
  2. Restore it at init, verify it before every activation, and raise it only after a confirmed successful boot.
  3. Separate "rollback to previous slot" (crash recovery, allowed) from "install older version" (forbidden).

Acceptance: activate v5, reset, try to flash v3 → refused, including after power cycle.

P0-5. The seed generator is predictable on parts without a hardware RNG

Evidence: uds_security_app.c, csprng_generate_bytes. If the TRNG is unavailable (uds_platform_trng_get_random returns false on F1/C0-class parts and in the host build), it falls back to a pool that starts from a fixed constant and mixes in SysTick and a counter. The pool is deterministic given the SysTick value at request time, which correlates with time since boot. The function still returns true, and the callers discard the result with (void).

Impact: on those targets seeds are guessable, which defeats challenge-response even with a good key.

Fix

  1. If no true entropy source exists, refuse SecurityAccess seeds (fail closed) rather than fabricating them.
  2. Where hardware RNG exists (F4/F7/G4/L4 RNG), use it and check SEIS/CEIS error flags and add a timeout to the DRDY wait.
  3. On parts without RNG, seed from an ADC noise/temperature sensor plus persistent boot counter, run a health test, and document the limits, or use a device-unique nonce sealed with the key.
  4. Check every return value (remove the (void) casts).

P1: Standards conformance, correctness, dead code

P1-1. Reserved STmin values abort the transfer (ISO 15765-2)

Evidence: isotp.c:67 valid_st_min() accepts only 0x00–0x7F and 0xF1–0xF9; isotp_tx_feed_flow_control then resets the transmission and returns ISOTP_ERR_FLOW_CONTROL for anything else. ISO 15765-2 says a sender that receives a reserved STmin (0x80–0xF0, 0xFA–0xFF) must use the longest STmin (0x7F, 127 ms) and keep going.

Impact: a tester with a quirky FC value kills a working transfer; interoperability risk.

Fix: map reserved values to 127 ms in st_min_ms() / st_min_us() and accept the frame. Add tests for every reserved value.

P1-2. Two security implementations; the tested one is unused

Evidence: uds_security_gate.c (100% coverage, own test) is referenced only by its header, tests and CMake. uds.c keeps its own copy of the same state (security_failed_attempts, security_lockout_until_ms, seed timers). The two already differ (the gate defaults to 3 attempts / 10 s, the server logic differs on reset).

Impact: coverage numbers and tests give false assurance; fixes to one copy never reach the other.

Fix: make UdsServer embed a UdsSecurityGate and delete the duplicate state in uds.c. Then apply P0-3 once, in one place.

P1-3. Classic-CAN frame length rules are not enforced

Evidence: rx_first accepts any DLC ≥ 2 and rx_consecutive any DLC ≥ 1 on classic CAN. ISO 15765-2 requires a first frame and every non-final consecutive frame to be full-length.

Fix: reject short FF/CF on classic CAN (except the final CF), with tests. Low risk, improves interoperability with strict testers.

P1-4. Bootloader metadata is trusted on a magic value only

Evidence: uds_bootloader.c:100 and :776 check meta->magic and nothing else.

Fix: add a CRC-32 (or hash) over the metadata block itself, plus a format version, and treat mismatch as "no valid image".

P1-5. Ignored return values in security-relevant paths

Evidence: (void)csprng_generate_bytes(...) (twice), (void)memset etc. The first two matter.

Fix: propagate the error to NRC 0x22/0x10, and add -Wunused-result / warn_unused_result on such functions.

P2: Architecture

P2-1. Move DTC and bootloader logic out of App/

App/Src/uds_dtc_app.c (1,345 lines) and uds_bootloader.c (929 lines) still hold real logic. Only library/ is host-tested without STM32 headers, so the two places where the most defects appeared cannot be tested fully on a PC. Move the logic to library/src/dtc_store.c, boot_slots.c, boot_routines.c, keep only board glue in App/.

P2-2. Replace file-scope singletons with instances

static UdsBootloaderContext s_bl_ctx, static keys and seeds in uds_security_app.c, and uds_server_get_current() make the code single-instance and hard to test in parallel. Pass a context pointer everywhere (the library core already does).

P2-3. Clean up ports/

Under my strict flags the five port files still produce 10 warnings (missing prototypes). Add -Werror for ports/ with the same flag set as library/, and keep the host contract test.

P2-4. One public error model

Mixed bool, UdsCallbackResult, UdsDownloadResult, IsoTpStatus. Document the mapping to NRCs in one table and enforce it with a test that walks every result code.

P3: Verification depth

P3-1. Make the fuzzers reach real code

fuzz_uds_request zeroes every callback (memset(&callbacks, 0, ...)), so it mostly exercises parsing. My two 30-second runs (1.2M ISO-TP, 6.2M UDS executions) found no crashes, which is good but shallow.

  • Provide in-memory implementations of DID, memory, download, DTC and security callbacks.
  • Make the harness stateful: interpret the input as a sequence of requests with time steps.
  • Add targets for the bootloader routine-control state machine, DTC report, and download/transfer sequence.
  • Commit a seed corpus and a dictionary of service IDs.
  • Run 5 minutes per PR, hours nightly.

P3-2. Security regression tests for every P0 item

Forged signature rejected; unprovisioned device cannot unlock; lockout survives 0x11 and power cycle; rollback refused after reset; seed generation fails closed with no entropy.

P3-3. Reconcile the branch-coverage number

CI is green with an 80% branch gate, but I measured 76.5% (gcovr 8.6) and 76.7% (gcovr 7.0) with the CI flags. The commit message says 81.7%. Publish the gcovr HTML report as a CI artifact, print the exact number in the log, and list the per-file minimum.

P3-4. Static analysis

  • MISRA: docs/misra_deviations.md exists but no checker runs. Add cppcheck with the MISRA addon (or a commercial tool) and fail on new violations, or remove the claim.
  • Run cppcheck with --force (it currently checks only 12 configurations).
  • Resolve or suppress-with-reason the GCC analyzer note at uds_wear_leveling.c:212 (src + written flagged uninitialized; the header is filled by memset first, so I believe it is a false positive).

P3-5. Timing and load tests on real silicon

Host tests use an injected clock. Add a bench test for STmin (0–127 ms and 100–900 µs), N_Bs/N_Cr timeouts, P2/P2*, and bus load ≥ 80%.

P4: Physical-validation evidence

  • 27 fields in docs/physical_validation/board_profile.yaml are still TBD and the verdict is NOT RUN. That is honest; now fill it with real data.
  • For each test ID record: board, firmware hash, tool, raw trace file (.asc/.blf/.pcapng), verdict. There are no traces in the repo today.
  • Choose the CAN FD + BRS board (still requires-selected-board).
  • Run the destructive flash/reset campaign only with a signed plan and a recovery procedure.
  • Never mark a board verified-on-hardware without the trace attached (a previous commit did and it was correctly reverted).

P5: Process and project health

  1. Second maintainer + branch protection: required review on main, signed tags, no force-moving release tags (v1.6.0 was moved once and restored).
  2. Release integrity: CI checks VERSION/changelog/uds_version.h agree; extend it to check the tag points at the released commit.
  3. Docs vs code: make README, PRODUCT_SCOPE and CHANGELOG say exactly what the code does. Anything called "signature", "anti-rollback" or "secure" must match the behaviour above, or be renamed.
  4. SBOM and third-party notices for HAL/CMSIS; pin CI tool versions (gcovr, clang, cppcheck) so coverage numbers are reproducible.
  5. Security policy: private vulnerability reporting, a fix SLA, and a CVD process.

P6: Polish and later

  • Use the hardware AES/CRC peripherals where present; keep the software AES only as a fallback and mark it non-constant-time.
  • Independent review of aes.c and sha256.c (known-answer tests exist; side-channel behaviour does not).
  • Implement the remaining ISO 14229 services and sub-functions you actually claim, with a conformance matrix (requirement → code → test → trace).
  • API stability policy and deprecation rules.
  • Nightly job that builds every example for every target and every flash-granule setting.
  • Tier 2 (ISO 26262, ISO/SAE 21434, ASPICE) only if the goal is OEM qualification.
